# Схема project.db

Описание переносимого ядра проектной базы: двух таблиц, `summaries` и
`neutered_summaries`. Документ самодостаточен — по нему можно поднять базу с
нуля, не читая код blind_prophet.

Схема корпуса (`corpus.db`) описана отдельно и здесь не дублируется:
`~/workspace/amnesiacDB/SCHEMA.md`. Фактический состав этой копии — в
`MANIFEST.yaml` рядом.

> Портируемая копия документа из `~/workspace/blind_prophet/docs/project_db_schema.md`.
> Оригинал живёт вместе с миграциями blind_prophet и будет меняться вслед за
> ними. Здесь — снимок на 2026-09-02; с этого момента базы и документы
> расходятся, и это нормально.

## Зачем отдельная база

Данные разложены на два хранилища:

| | Корпус | Проектная база |
|---|---|---|
| Что | новости, их эмбеддинги, векторы осей | результаты работы пайплайна над новостями |
| Файл | `corpus.db` → `~/workspace/amnesiacDB/corpus.db` | `project.db` |
| Кому | общий для нескольких проектов | у каждого проекта своя |
| Доступ | read-only | чтение и запись |

Джойнов между базами нет, поэтому `ATTACH` не нужен — держите два отдельных
соединения. Связь между хранилищами не по внешнему ключу, а по смыслу:
`(run_date, horizon_days)` задают окно, из которого брались новости.

## Создание с нуля

```sql
CREATE TABLE summaries (
    id            INTEGER PRIMARY KEY,
    run_date      TEXT NOT NULL UNIQUE,
    horizon_days  INTEGER NOT NULL CHECK (horizon_days > 0),
    summary       TEXT NOT NULL,
    doc_count     INTEGER,
    model         TEXT,
    created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    failed_axes   TEXT
);

CREATE TABLE neutered_summaries (
    run_date                  TEXT PRIMARY KEY,
    summary                   TEXT NOT NULL,
    neutering_status          TEXT NOT NULL,
    final_iteration           INTEGER,
    q3_preservation           REAL,
    raw_period_id_score       REAL,
    neutered_period_id_score  REAL,
    period_delta_vs_raw       REAL,
    judge_blind               INTEGER,
    model_n                   TEXT,
    model_j1                  TEXT,
    model_j2                  TEXT,
    created_at                TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

Расширений SQLite не требуется: векторов здесь нет, всё живёт в корпусе.
Журнал — WAL. База маленькая (при 13 саммари — чуть больше мегабайта), растёт
линейно по числу прогонов.

## `summaries`

Саммари новостей за период, результат отбора по осям и двухэтапной
суммаризации.

| Колонка | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | INTEGER PK | авто | суррогатный ключ |
| `run_date` | TEXT UNIQUE | да | дата, на которую делается срез, `YYYY-MM-DD` |
| `horizon_days` | INTEGER | да | сколько дней назад от `run_date` собирались новости |
| `summary` | TEXT | да | текст саммари |
| `doc_count` | INTEGER | нет | сколько документов ушло в суммаризацию |
| `model` | TEXT | нет | модель суммаризации |
| `created_at` | TIMESTAMP | авто | когда посчитано |
| `failed_axes` | TEXT | нет | JSON-массив осей, по которым саммари не собралось |

### Окно сбора

`run_date` и `horizon_days` вместе задают интервал, из которого брались новости:

```
date_from = run_date - horizon_days дней
date_to   = run_date
```

**Сам `run_date` в окно не входит.** Отбор идёт запросом
`date BETWEEN date_from AND date_to`, где границы — голые даты (`'2020-04-20'`),
а `messages.date` в корпусе хранится полным ISO-таймстампом
(`'2020-04-20T10:00:00+00:00'`). Сравнение строковое, поэтому любой таймстамп
внутри `run_date` оказывается больше границы и отсекается.

Фактическое окно — `horizon_days` полных суток, заканчивающихся **накануне**
`run_date`:

```
[run_date - horizon_days, run_date)
```

Проверено на данных: для `run_date = 2020-04-20`, `horizon_days = 14` выборка
содержит сообщения с `2020-04-06T00:06` по `2020-04-19T23:45`, а все 478
сообщений за 20 апреля в неё не попадают.

Для прогнозной задачи это правильно — новости дня опроса не должны утекать в
предсказание, — но полагаться стоит на явное правило, а не на побочный эффект
сравнения строк. Если воспроизводите выборку и передаёте границы как
`datetime`, а не как строки, вы получите **другой** набор документов: день
`run_date` попадёт внутрь. Либо повторяйте строковую семантику, либо задавайте
верхнюю границу явно, с исключающим сравнением `<`.

### Почему `horizon_days` в базе, а не только в конфиге

Одна и та же `run_date` с разным горизонтом даёт разное саммари. Пока горизонт
живёт только в конфиге, строка в базе не говорит, из какого периода она
собрана: поменяли конфиг — и старые строки молча стали неинтерпретируемыми.
Это единственная колонка, без которой саммари невоспроизводимо, поэтому она
`NOT NULL`.

### `UNIQUE(run_date)` — одно саммари на дату

База хранит **один** актуальный результат на дату, а не историю попыток.
Перезапись — через `INSERT OR REPLACE`.

Практическое следствие: сравнить два горизонта на одной дате (скажем, 7 и 30
дней) текущая схема не даст — вторая запись затрёт первую. Если такая задача
появится, ключ надо расширять до `UNIQUE(run_date, horizon_days)`, а заодно,
вероятно, и до модели.

### `failed_axes` — из скольких осей собрано саммари

Расхождение с оригиналом blind_prophet: колонка добавлена здесь, миграция —
`migrations/012_summaries_failed_axes.sql`.

Двухэтапная суммаризация собирает мету из девяти осевых саммари, и при
`max_failed_axes > 0` результат считается успешным, даже если часть осей
отвалилась. Пока в базе лежал только текст, дата с восемью осями из девяти была
неотличима от полной: при чтении из кеша сведения об отказах терялись, и
единственным их следом оставался артефакт прогона. Случай, ради которого
колонка появилась, — 2026-02-26, ось `курс`: провайдер вернул пустой ответ,
саммари ушло в кеш как обычное.

Формат — JSON-массив имён осей, `ensure_ascii=False`:

| Значение | Смысл |
|---|---|
| `NULL` | **неизвестно**: строка записана до миграции |
| `'[]'` | проверено, не отвалилось ничего |
| `'["курс"]'` | саммари собрано без оси `курс` |

`NULL` и `'[]'` смешивать нельзя. Тринадцать унаследованных от blind_prophet
строк честно неизвестны, и приравнивать их к «всё в порядке» значит вернуть ту
самую невидимую деградацию, против которой колонка и заведена.

### Примеры

```sql
INSERT OR REPLACE INTO summaries
    (run_date, horizon_days, summary, doc_count, model, failed_axes)
VALUES (?, ?, ?, ?, ?, ?);
```

```sql
-- даты, чьё саммари заведомо неполно
SELECT run_date, failed_axes
FROM summaries
WHERE failed_axes IS NOT NULL AND failed_axes != '[]';
```

```sql
-- восстановить окно сбора для каждой даты
SELECT run_date,
       date(run_date, '-' || horizon_days || ' days') AS date_from,
       run_date AS date_to,
       doc_count
FROM summaries
ORDER BY run_date;
```

## `axis_summaries`

Расхождение с оригиналом blind_prophet: таблица добавлена здесь, миграция —
`migrations/013_axis_summaries.sql`.

Осевые саммари первого этапа — то, из чего собрана мета в `summaries`. До этой
таблицы они выбрасывались: девять вызовов модели на дату существовали только
внутри одного вызова `amnesiac.summarize()` и нигде не сохранялись.

| Колонка | Тип | Обяз. | Смысл |
|---|---|---|---|
| `run_date` | TEXT | да | дата среза, часть первичного ключа |
| `axis` | TEXT | да | имя оси, часть первичного ключа |
| `horizon_days` | INTEGER | да | горизонт окна |
| `model` | TEXT | нет | модель суммаризации |
| `summary` | TEXT | да | текст осевого саммари |
| `doc_count` | INTEGER | нет | сколько документов отобрано по этой оси |
| `created_at` | TIMESTAMP | авто | когда посчитано |

Ключ `(run_date, axis)`: на дату по строке на ось, как в `summaries` одна строка
на дату. `horizon_days` и `model` дублируются здесь намеренно — строка должна
быть интерпретируема без джойна, по тем же соображениям, что и в `summaries`.

**Отказавшие оси сюда не пишутся.** Вместо текста `amnesiac` подставляет
заглушку `(нет данных по оси из-за ошибки провайдера)`, и хранить её как саммари
значило бы выдать отсутствие данных за данные. Какие оси отвалились, записано в
`summaries.failed_axes`; отсюда они просто отсутствуют.

Чего таблица **не** даёт: спасти работу при провале мета-этапа. В `amnesiac`
осевые саммари — локальная переменная, и `SummarizeError` при пустой мете не
несёт их с собой. То есть ровно в тот момент, когда девять посчитанных осей
жалко терять, сохранять нечего. Запись происходит только после полного успеха.

```sql
-- что модель писала про одну ось в разные периоды
SELECT run_date, doc_count, summary
FROM axis_summaries
WHERE axis = 'дкп' AND horizon_days = 14
ORDER BY run_date;
```

```sql
-- даты, где мета собрана не из всех девяти осей
SELECT s.run_date, s.failed_axes, count(a.axis) AS axes_stored
FROM summaries s LEFT JOIN axis_summaries a ON a.run_date = s.run_date
GROUP BY s.run_date
HAVING axes_stored < 9;
```

## `migrations`

База ведёт реестр применённых миграций — таблица `migrations (name, applied_at)`,
унаследованная от blind_prophet вместе со схемой. На момент форка в ней было
пять записей, до `011_summaries_horizon_days`.

Миграции этого проекта продолжают ту же нумерацию с `012` и лежат в
`data/newsDB/migrations/`. С этого номера последовательность локальная: если
blind_prophet заведёт собственную `012`, номера совпадут при разном содержании.
Расхождение осознанное, оно того же рода, что и расхождение самих схем.

Применяются вручную, инструмента миграций в проекте нет:

```bash
sqlite3 data/newsDB/project.db < data/newsDB/migrations/013_axis_summaries.sql
sqlite3 data/newsDB/project.db "INSERT INTO migrations (name) VALUES ('013_axis_summaries');"
```

Идемпотентности в `ALTER TABLE` и `CREATE TABLE` без `IF NOT EXISTS` нет:
повторный запуск упадёт, и это нормально — реестр показывает, что уже применено.

## `neutered_summaries`

Саммари после нейтрализации — итеративного удаления маркеров, по которым можно
опознать конкретный период (даты, имена, события-якоря). Задача: оставить
экономическое содержание, убрав возможность датировать текст.

Ключ — `run_date`, то есть один-к-одному с `summaries`. Внешнего ключа нет
намеренно: таблицы могут жить в разных базах, а строка-сирота допустима, если
исходное саммари удалили.

| Колонка | Тип | Смысл |
|---|---|---|
| `run_date` | TEXT PK | та же дата, что в `summaries` |
| `summary` | TEXT | нейтрализованный текст |
| `neutering_status` | TEXT | исход цикла, см. ниже |
| `final_iteration` | INTEGER | на какой итерации остановились |
| `q3_preservation` | REAL | доля сохранённого содержания, 0..1 |
| `raw_period_id_score` | REAL | насколько судья датирует исходный текст, 0..1 |
| `neutered_period_id_score` | REAL | то же для нейтрализованного |
| `period_delta_vs_raw` | REAL | `raw - neutered`, выигрыш нейтрализации |
| `judge_blind` | INTEGER | 1, если судья не смог датировать даже исходник |
| `model_n` | TEXT | модель, выполнявшая нейтрализацию |
| `model_j1` | TEXT | судья внутри цикла |
| `model_j2` | TEXT | независимый судья на holdout |
| `created_at` | TIMESTAMP | когда посчитано |

### `neutering_status`

Четыре исхода, различать их важно — это не просто «получилось / не получилось»:

| Значение | Что произошло |
|---|---|
| `neutered` | успех: маркеры убраны, содержание сохранено |
| `residual_hard_fail` | остались жёсткие маркеры, которые не удалось убрать |
| `signal_collapse` | вместе с маркерами вымылось само содержание |
| `hard_capped` | кончился лимит итераций, дошли до потолка |

`signal_collapse` и `residual_hard_fail` — противоположные отказы: в первом
случае вычистили слишком много, во втором слишком мало. Строки с такими
статусами в базе остаются: это результат, а не ошибка, и их надо учитывать при
разборе прогонов, а не молча фильтровать.

### Метрики

**`q3_preservation`** — сколько содержания пережило нейтрализацию, 0..1.
Считается сравнением ответов на контрольные вопросы к исходному и
нейтрализованному тексту. Ниже порога цикл фиксирует `signal_collapse`
(в blind_prophet порог `Y_FLOOR = 0.70`).

**`raw_period_id_score` / `neutered_period_id_score`** — насколько уверенно
независимый судья определяет период по тексту, 0..1. Усредняются по нескольким
сэмплам (в blind_prophet — 5) и взвешиваются по близости названного периода к
настоящему. Нейтрализация работает, когда второе заметно меньше первого.

**`period_delta_vs_raw`** — разность `raw - neutered`, хранится посчитанной,
чтобы не пересчитывать в запросах.

**`judge_blind`** — служебный флаг качества измерения. Ставится в 1, когда
`raw_period_id_score` ниже порога (в blind_prophet 0.4), то есть судья не смог
датировать даже **исходный** текст. В таких строках дельта ничего не значит:
измерять снижение не от чего. **Строки с `judge_blind = 1` надо исключать из
любой агрегированной оценки эффекта** — иначе они разбавят среднее нулями,
которые выглядят как «нейтрализация не помогла», хотя на деле не сработал
инструмент измерения.

### Пример

```sql
-- сводка по прогонам с честными измерениями
SELECT n.run_date,
       n.neutering_status,
       s.horizon_days,
       round(n.q3_preservation, 3)     AS preserved,
       round(n.period_delta_vs_raw, 3) AS delta
FROM neutered_summaries n
JOIN summaries s ON s.run_date = n.run_date
WHERE n.judge_blind = 0
ORDER BY n.run_date;
```

## Порядок записи

```
corpus.db (read-only)
  → отбор по осям за окно [run_date - horizon_days, run_date)
  → суммаризация            → summaries
  → нейтрализация           → neutered_summaries
```

`neutered_summaries` пишется только после того, как для этой `run_date` есть
строка в `summaries`: нейтрализация читает исходный текст оттуда.

Обе записи идемпотентны по `run_date` (`INSERT OR REPLACE`), поэтому повторный
прогон даты безопасен и заменяет предыдущий результат.

## Что в переносимое ядро не входит

В этой копии есть ещё `forecasts` и `infom_expectations` — наследство
blind_prophet. Первая завязана на набор персон и модель прогноза, вторая — на
целевой ряд опросов инФОМ. Схема ядра от их удаления не пострадает.

Правило на будущее: всё, что зависит от постановки задачи конкретного проекта
(кеши, промежуточные артефакты, целевые ряды), заводится в проектной базе, а не
в общем корпусе.

## Миграции

Схемой проектной базы владеет сам проект — в отличие от корпуса, схемой
которого владеет репозиторий amnesiacDB.

В скопированной базе ledger применённых миграций лежит в таблице `migrations`;
нумерация историческая, с пропусками (`007`–`011`, см. `MANIFEST.yaml`). Если
поднимаете базу заново — нумеруйте с `001` по DDL из раздела «Создание с
нуля», он уже учитывает все изменения.
