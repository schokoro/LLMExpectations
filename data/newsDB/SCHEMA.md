# Схема project.db

Описание проектной базы `LLMExpectations`: `summaries`, `axis_summaries`,
`infom_expectations` и реестр `migrations`. Документ самодостаточен — по нему
можно поднять базу с нуля, не читая код blind_prophet.

По D-027 этот документ **нормативен для всех потребителей `amnesiac`**, а не
только для этого проекта: состав и типы колонок `summaries` и `axis_summaries`,
семантика `failed_axes`, сквозная нумерация миграций и обязательность реестра.
Расхождение, введённое одним потребителем, вносится сюда с указанием, у кого оно
действует; молчаливый разъезд схем — дефект, а не свойство.

Схема корпуса (`corpus.db`) описана отдельно и здесь не дублируется:
`~/workspace/amnesiacDB/SCHEMA.md`. Фактический состав этой копии — в
`MANIFEST.yaml` рядом.

> Документ вырос из портируемой копии `~/workspace/blind_prophet/docs/project_db_schema.md`
> (снимок на 2026-09-02). С тех пор базы и документы разошлись: описание
> приведено к состоянию после миграций `012`–`014` и очистки D-026.

## Зачем отдельная база

Данные разложены на два хранилища:

| | Корпус | Проектная база |
|---|---|---|
| Что | новости, их эмбеддинги, векторы осей | результаты работы пайплайна над новостями |
| Файл | `corpus.db` → `~/workspace/amnesiacDB/corpus.db` | `project.db` |
| Кому | общий для нескольких проектов | у каждого проекта своя |
| Доступ | read-only | чтение и запись |

Джойнов между базами нет, поэтому `ATTACH` не нужен — держите два отдельных
соединения. Связь между хранилищами не по внешнему ключу, а по смыслу:
`(run_date, horizon_days)` задают окно, из которого брались новости.

## Состав базы

Четыре таблицы:

| Таблица | Кто пишет | Назначение |
|---|---|---|
| `summaries` | пайплайн этого проекта | мета-саммари на дату |
| `axis_summaries` | пайплайн этого проекта | осевые саммари первого этапа |
| `infom_expectations` | никто, унаследована | целевой ряд опросов инФОМ |
| `migrations` | руками при миграции | реестр применённых миграций |

`neutered_summaries` и `forecasts` из этой базы удалены миграцией
`014_drop_blind_prophet_tables` — это данные blind_prophet, они живут в
оригинальной базе того проекта. Entity neutering в первом baseline не
применяется (D-004).

`infom_expectations` пайплайном не пишется и не читается, но удалять её нельзя:
это эталонный ряд для контура оценки (эпик E02), и взять его заново неоткуда.

## Создание с нуля

```sql
CREATE TABLE summaries (
    id            INTEGER PRIMARY KEY,
    run_date      TEXT NOT NULL UNIQUE,
    horizon_days  INTEGER NOT NULL CHECK (horizon_days > 0),
    summary       TEXT NOT NULL,
    doc_count     INTEGER,
    model         TEXT,
    created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    failed_axes   TEXT,
    config_hash   TEXT
);

CREATE TABLE axis_summaries (
    run_date      TEXT NOT NULL,
    axis          TEXT NOT NULL,
    horizon_days  INTEGER NOT NULL CHECK (horizon_days > 0),
    model         TEXT,
    summary       TEXT NOT NULL,
    doc_count     INTEGER,
    created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    config_hash   TEXT,
    PRIMARY KEY (run_date, axis)
);

CREATE TABLE migrations (
    name        TEXT PRIMARY KEY,
    applied_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

Расширений SQLite не требуется: векторов здесь нет, всё живёт в корпусе.
Журнал — WAL, поэтому рядом с файлом появляются `-wal`/`-shm`; их создаёт любой
читатель, включая `mode=ro`, и они закрыты `.gitignore`.

## `summaries`

Саммари новостей за период, результат отбора по осям и двухэтапной
суммаризации.

| Колонка | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | INTEGER PK | авто | суррогатный ключ |
| `run_date` | TEXT UNIQUE | да | дата, на которую делается срез, `YYYY-MM-DD` |
| `horizon_days` | INTEGER | да | сколько дней назад от `run_date` собирались новости |
| `summary` | TEXT | да | текст саммари |
| `doc_count` | INTEGER | нет | сколько документов ушло в суммаризацию |
| `model` | TEXT | нет | модель суммаризации |
| `created_at` | TIMESTAMP | авто | когда посчитано |
| `config_hash` | TEXT | нет | SHA-256 значимых параметров конфигурации; несовпадение или NULL — промах кеша |
| `failed_axes` | TEXT | нет | JSON-массив осей, по которым саммари не собралось |

### Окно сбора

`run_date` и `horizon_days` вместе задают интервал по московскому времени, из
которого брались новости:

```
[run_date - horizon_days, run_date)
```

Окно — `horizon_days` полных московских суток, заканчивающихся **накануне**
`run_date`; день `run_date` исключён целиком. Правило зафиксировано в D-015 и
`docs/news_rag.md` v1.0. В UTC-терминах корпуса интервал имеет вид
`[run_date - horizon_days - 1 день 21:00Z, run_date - 1 день 21:00Z)`.
Московское время на всём периоде корпуса имеет фиксированное смещение `UTC+3`:
переходов на летнее время нет с 2011 года, а корпус начинается в марте 2016-го.

Обе границы передаются как полные ISO-таймстампы UTC и применяются явно:
`date >= ? AND date < ?`.

**Прежняя ловушка теперь действует наоборот:** голые календарные даты задают
неверное окно. Они сдвигают обе границы на три часа: захватывают
`00:00–03:00 MSK` дня опроса и теряют те же три часа в начале периода.

`day_number` считается от московской даты публикации. Покрытие считается в
полных московских сутках, частичные дни по краям исключены; живое покрытие —
`2016-03-22 … 2026-04-11`. Обратите внимание, что `MANIFEST.yaml` корпуса даёт
сырые крайние таймстампы (`2016-03-21T16:09:08+00:00` и
`2026-04-12T00:57:29+00:00`) — это не противоречие, а другой способ счёта: по
московским суткам крайние дни неполны и в покрытие не входят.

**Строковое сравнение границ держится на непроверяемом инварианте.** Оно
допустимо, потому что формат `messages.date` однороден: все 1 288 233 строки
корпуса имеют длину 25 символов и суффикс `+00:00`, поэтому строковый и
хронологический порядок совпадают. Замер сделан руками один раз и в рантайме не
проверяется. Корпус, пересобранный с другим разделителем или локальным
смещением, сдвинет окно молча — тот же класс отказа, что снят переходом на MSK,
слоем ниже. Место для охраны: `assertCorpusContract()`.

Кеш саммари очищен целиком по D-026: строки, посчитанные до перехода на
московское окно, были несопоставимы с новыми, а ключ
`(run_date, horizon_days, model)` их не различает. На момент правки документа
`summaries` и `axis_summaries` пусты.

### Почему `horizon_days` в базе, а не только в конфиге

Одна и та же `run_date` с разным горизонтом даёт разное саммари. Пока горизонт
живёт только в конфиге, строка в базе не говорит, из какого периода она
собрана: поменяли конфиг — и старые строки молча стали неинтерпретируемыми.
Это единственная колонка, без которой саммари невоспроизводимо, поэтому она
`NOT NULL`.

Правило часового пояса, порядок осей и провайдер маршрутизации входят в
`config_hash` (D-031). Обе таблицы сверяют его вместе с горизонтом и моделью;
манифест прогона (D-025) должен использовать тот же метод `configHash()`.

### `config_hash` — конфигурация обоих уровней кеша

Расхождение с blind_prophet: миграция `015_summaries_config_hash.sql` добавляет
`config_hash TEXT` в обе таблицы. Метод `NewsRagConfiguration.configHash()` —
единственный источник хеша для кеша и будущего манифеста. Чтение сверяет
`(run_date, horizon_days, model, config_hash)`; для осевых строк также `axis`.
Иной хеш или `NULL` означает отсутствие подходящей строки. Физические ключи
`UNIQUE(run_date)` и `PRIMARY KEY(run_date, axis)` не меняются: запись заменяет
предыдущую конфигурацию, история не сохраняется. Отсутствующая колонка в любой
таблице — ошибка с указанием миграции, а не разрешение использовать старый кеш.
Обе таблицы перед применением пусты; значения по умолчанию и back-fill не нужны.

Состав JSON в фактическом порядке сериализации (ключи отсортированы):

1. `axes`: список пар `[имя оси, [запрос, ...]]` в порядке `configuration.axes`;
   учитываются и порядок осей, и точные тексты запросов.
2. `dedupThreshold`.
3. `excludeChannels` (список).
4. `mode`.
5. `moscowUtcOffsetHours` (сейчас `3`).
6. `summarizeBaseUrl`.
7. `summarizeMaxFailedAxes`.
8. `summarizePromptPack`: `RU_MACRO_V1.model_dump(exclude={'params'})` до `bind`.
   Внутренние ключи также сортируются: `axis_block_separator`,
   `axis_block_template`, `axis_system`, `axis_user`, `doc_separator`,
   `doc_template`, `meta_system`, `meta_user`, `name`. Хешируются реальные
   тексты шаблонов и разделителей, а не только имя пакета.
9. `summarizeProvider` (по умолчанию `deepinfra/fp8`; провайдер закреплён
   в каждом запросе суммаризации и участвует в `config_hash`).
10. `summarizeTemperature`.
11. `topKPerAxis`.
12. `windowRule`: литерал `full_moscow_days_survey_day_excluded`, обозначающий
    полные московские сутки с исключением всего дня опроса (D-015).

Каноническая сериализация: `json.dumps(payload, sort_keys=True,
separators=(',', ':'), ensure_ascii=False)`, затем UTF-8 и SHA-256 hex.
Порядок ключей объектов и исходное форматирование не влияют на результат;
порядок осей сохраняется массивом пар и влияет. При изменении семантики окна
нужно менять `windowRule`, даже если смещение часового пояса осталось прежним.

Намеренно исключены:

- `horizonDays`, `summarizeModel`: уже сверяются отдельными частями ключа.
- `summarizeConcurrency`, `summarizeTimeout`: параметры скорости выполнения.
- `summarizeApiKeyVariable`: имя источника секрета, а не параметр результата.
  Значение ключа не читается для хеша и не попадает в логи или артефакты.
- `corpusPath`, `projectDbPath`, `artefactsFolder`: расположение файлов.
- `params` пакета промптов: связанный `horizon_days` иначе дублировал бы ключ.

Хеш не кодирует изменения алгоритма при неизменных параметрах. Ручная
инвалидация по D-031 по-прежнему очищает **обе** таблицы вместе.

### `UNIQUE(run_date)` — одно саммари на дату

База хранит **один** актуальный результат на дату, а не историю попыток.
Перезапись — через `INSERT OR REPLACE`.

Практическое следствие: сравнить два горизонта на одной дате (скажем, 7 и 30
дней) текущая схема не даст — вторая запись затрёт первую. Если такая задача
появится, ключ надо расширять до `UNIQUE(run_date, horizon_days)`, а заодно,
вероятно, и до модели. По D-027 это правка нормативной схемы, то есть возможный
триггер выделения общей базы в отдельный репозиторий.

### `failed_axes` — из скольких осей собрано саммари

Расхождение с оригиналом blind_prophet: колонка добавлена здесь, миграция —
`migrations/012_summaries_failed_axes.sql`.

Двухэтапная суммаризация собирает мету из девяти осевых саммари, и при
`max_failed_axes > 0` результат считается успешным, даже если часть осей
отвалилась. Пока в базе лежал только текст, дата с восемью осями из девяти была
неотличима от полной: при чтении из кеша сведения об отказах терялись, и
единственным их следом оставался артефакт прогона. Случай, ради которого
колонка появилась, — 2026-02-26, ось `курс`: провайдер вернул пустой ответ,
саммари ушло в кеш как обычное.

Формат — JSON-массив имён осей, `ensure_ascii=False`:

| Значение | Смысл |
|---|---|
| `NULL` | **неизвестно**: строка записана до миграции |
| `'[]'` | проверено, не отвалилось ничего |
| `'["курс"]'` | саммари собрано без оси `курс` |

`NULL` и `'[]'` смешивать нельзя. В этой базе строк с `NULL` больше нет —
унаследованные удалены вместе с остальным кешем, — но состояние остаётся частью
контракта: колонка снова станет `NULL` при чтении чужой базы или строки,
записанной кодом без миграции. Приравнивать `NULL` к «всё в порядке» значит
вернуть ту самую невидимую деградацию, против которой колонка и заведена.

**В кеш кладутся только оси, которых нет в `failed_axes`.** Заглушка
`(нет данных по оси из-за ошибки провайдера)` саммари не является; сохранив её,
вы получите ось, которая никогда не пересчитается, и дату с дыркой,
неотличимую от успеха (`amnesiac` api.md §5.9).

### Примеры

```sql
INSERT OR REPLACE INTO summaries
    (run_date, horizon_days, summary, doc_count, model, failed_axes, config_hash)
VALUES (?, ?, ?, ?, ?, ?, ?);
```

```sql
SELECT run_date, failed_axes
FROM summaries
WHERE failed_axes IS NOT NULL AND failed_axes != '[]';
```

## `axis_summaries`

Расхождение с оригиналом blind_prophet: таблица добавлена здесь, миграция —
`migrations/013_axis_summaries.sql`.

Осевые саммари первого этапа — то, из чего собрана мета в `summaries`. До этой
таблицы они выбрасывались: девять вызовов модели на дату существовали только
внутри одного вызова `amnesiac.summarize()` и нигде не сохранялись.

| Колонка | Тип | Обяз. | Смысл |
|---|---|---|---|
| `run_date` | TEXT | да | дата среза, часть первичного ключа |
| `axis` | TEXT | да | имя оси, часть первичного ключа |
| `horizon_days` | INTEGER | да | горизонт окна |
| `model` | TEXT | нет | модель суммаризации |
| `summary` | TEXT | да | текст осевого саммари |
| `doc_count` | INTEGER | нет | сколько документов отобрано по этой оси |
| `created_at` | TIMESTAMP | авто | когда посчитано |
| `config_hash` | TEXT | нет | SHA-256 значимых параметров конфигурации; несовпадение или NULL — промах кеша |

Ключ `(run_date, axis)`: на дату по строке на ось, как в `summaries` одна строка
на дату. `horizon_days` и `model` дублируются здесь намеренно — строка должна
быть интерпретируема без джойна, по тем же соображениям, что и в `summaries`.

**Отказавшие оси сюда не пишутся.** Вместо текста `amnesiac` подставляет
заглушку `(нет данных по оси из-за ошибки провайдера)`, и хранить её как саммари
значило бы выдать отсутствие данных за данные. Какие оси отвалились, записано в
`summaries.failed_axes`; отсюда они просто отсутствуют.

### Таблица несёт дешёвый повтор

С `amnesiac` v0.2.0 осевые саммари сохраняются **до** мета-вызова, и таблица
перестала быть только хранилищем для анализа: провал меты стоит один вызов
вместо десяти (D-028). Прежнее ограничение — «спасти работу при провале
мета-этапа нельзя, осевые саммари живут локальной переменной» — снято:
`MetaSummaryError` несёт результат первой стадии целиком, `TooManyAxisFailures`
несёт посчитавшиеся оси, а раздельные стадии `summarize_axes()` /
`summarize_meta()` позволяют не доводить до исключения вовсе.

**Порядок ключей при склейке восстанавливается явно.** Досчитав хвост,
собирайте словарь как `{name: ready[name] for name in axes}`: наивное
объединение даёт «сначала кешированные, потом свежие», а порядок ключей
определяет порядок блоков мета-промпта (`amnesiac` api.md §5.10). Тот же
порядок осей — вход эксперимента и попадает в манифест прогона (D-014, D-025).

```sql
SELECT run_date, doc_count, summary
FROM axis_summaries
WHERE axis = 'дкп' AND horizon_days = 14
ORDER BY run_date;
```

```sql
SELECT s.run_date, s.failed_axes, count(a.axis) AS axes_stored
FROM summaries s LEFT JOIN axis_summaries a ON a.run_date = s.run_date
GROUP BY s.run_date
HAVING axes_stored < 9;
```

журнала решений.

## `migrations`

База ведёт реестр применённых миграций — таблица `migrations (name, applied_at)`,
унаследованная от blind_prophet вместе со схемой. На момент форка в ней было
пять записей, `007`–`011`, последняя `011_summaries_horizon_days`; более ранняя
нумерация относится ко временам, когда корпус и проектная база были одним файлом.

Миграции этого проекта продолжают ту же нумерацию с `012` и лежат в
`data/newsDB/migrations/`:

| Миграция | Что делает |
|---|---|
| `012_summaries_failed_axes` | колонка `failed_axes` в `summaries` |
| `013_axis_summaries` | таблица `axis_summaries` |
| `014_drop_blind_prophet_tables` | удаляет `neutered_summaries` и `forecasts` |
| `015_summaries_config_hash` | колонка `config_hash` в `summaries` и `axis_summaries` |

С номера `012` последовательность локальная: если blind_prophet заведёт
собственную `012`, номера совпадут при разном содержании. Расхождение
осознанное, оно того же рода, что и расхождение самих схем, и ограничено сроком
— по D-027 сквозная нумерация нормативна, а по триггеру заводится общая база.

Применяются вручную, инструмента миграций в проекте нет:

```bash
sqlite3 data/newsDB/project.db < data/newsDB/migrations/014_drop_blind_prophet_tables.sql
sqlite3 data/newsDB/project.db "INSERT INTO migrations (name) VALUES ('014_drop_blind_prophet_tables');"
```

Идемпотентности в `ALTER TABLE` и `CREATE TABLE` без `IF NOT EXISTS` нет:
повторный запуск упадёт, и это нормально — реестр показывает, что уже применено.

**Реестр правится тем же коммитом, что и схема.** Незарегистрированная миграция
неотличима от неприменённой, а зарегистрированная без файла — от применённой
(D-021). Именно поэтому удаление двух таблиц оформлено миграцией `014`, а не
разовой командой: иначе реестр утверждал бы, что `009` и `010` создали таблицы,
которых в базе нет.

## Порядок записи

```
corpus.db (read-only)
  → отбор по осям за окно [run_date - horizon_days, run_date)  (московское)
  → осевые саммари          → axis_summaries
  → мета-саммари            → summaries
```

Обе записи идемпотентны по ключу (`INSERT OR REPLACE`), поэтому повторный
прогон даты безопасен и заменяет предыдущий результат.

Нейтрализация в этом проекте не выполняется (D-004); в blind_prophet она идёт
третьим шагом и пишет в свою `neutered_summaries`.

## Правило на будущее

Всё, что зависит от постановки задачи конкретного проекта (кеши, промежуточные
артефакты, целевые ряды), заводится в проектной базе, а не в общем корпусе.
Обратное тоже верно: результаты чужого проекта в своей базе не держат — именно
поэтому `forecasts` и `neutered_summaries` отсюда удалены.

Схемой проектной базы владеет сам проект — в отличие от корпуса, схемой
которого владеет репозиторий amnesiacDB. Но с D-027 «свой проект» не значит
«как угодно»: этот документ нормативен для всех потребителей `amnesiac`.
